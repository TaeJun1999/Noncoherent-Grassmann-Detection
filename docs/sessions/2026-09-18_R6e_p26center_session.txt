이 저장소는 noncoherent MIMO 연구의 재현 코드다. 너의 일은 실험 하나를 코드 수정 없이
돌리고, 원시 로그를 저장소에 커밋해서 commit hash를 보고하는 것이다. 결과 해석은 하지
않는다. 로그는 다른 사람이 읽고 연구 기록에 옮긴다. 그래서 숫자를 요약하거나 반올림하거나
고쳐 적으면 안 되고, 파일에 남은 원문이 유일한 근거가 된다.

저장소: <REPO_URL>
로컬 경로: <REPO_DIR>   (없으면 위 URL을 이 경로에 clone)

## 순서

1. 저장소를 최신으로 맞춘다. `git status`로 작업 트리가 깨끗한지 먼저 본다. 커밋되지 않은
   변경이 있으면 건드리지 말고 멈춰서 보고한다. 깨끗하면 `git pull --ff-only`.
   pull 직후의 `git rev-parse HEAD`를 기록해 둔다 (이것이 "실행에 쓴 코드의 hash"다).

2. `p26_center_test.py`가 있는 디렉터리를 찾는다 (저장소 루트이거나 `code/`). 이후 모든
   실행은 그 디렉터리에서 한다. 스크립트가 `cubesplit_gap.py`를 상대 import하고, 리스트
   파일도 상대 경로로 읽고 쓰기 때문이다.

3. 결과 디렉터리를 만든다 (저장소 루트 기준):
   `results/R6e_p26center_T8_B01_N4_rho1.5_eta16_ncw300/`
   여기에 `env.txt`를 쓴다: `uname -a`, `nproc`, `free -g`, `python3 --version`,
   numpy·scipy 버전, 1번에서 기록한 hash. numpy나 scipy가 없으면 venv를 만들어 설치하고
   그 사실을 env.txt에 적는다.

4. 구현 검증을 먼저 돌린다 (약 3분):
   `python3 sanity.py 2>&1 | tee <결과 디렉터리>/sanity.log`
   assert가 실패하거나 예외가 나면 거기서 멈추고 보고한다. 환경이 다르면 본 실험 숫자도
   믿을 수 없기 때문이다.

5. 본 실험. 명령은 정확히 이것이다. 인자와 seed(코드에 5로 고정)를 바꾸지 않는다:
   `python3 -u p26_center_test.py 1.5 300 16`
   - 같은 디렉터리에 `lists_T8_B01_eta16.npy`가 없으면 스크립트가 리스트 사전계산부터
     한다. 약 9분 더 걸리고 메모리를 3 GB 가까이 쓴다. 정상 동작이다. 있었는지 없었는지
     기록한다.
   - 전체 12–25분이 걸린다. 도구 호출 시간 제한에 걸리지 않도록 배경으로 띄우고 폴링한다:
     `nohup python3 -u p26_center_test.py 1.5 300 16 > <결과 디렉터리>/stdout.log 2>&1 &`
     이후 1–2분 간격으로 `tail -n 2`를 확인한다. 마지막 줄이 `candidate set sizes:`로
     시작하면 끝난 것이다. 프로세스가 그 줄 없이 죽었으면 로그를 그대로 두고 보고한다.
   - 실행한 명령 원문, 시작·종료 시각(`date -Is`), npy 재사용 여부를 `cmd.txt`에 적는다.

6. 커밋과 push.
   - `lists_*.npy`는 약 285 MB다. GitHub가 100 MB 초과 파일을 거부하므로 절대 add하지
     않는다. `.gitignore`에 `lists_*.npy`가 없으면 한 줄 추가한다.
   - add 대상은 결과 디렉터리와 (바꿨다면) `.gitignore`뿐이다. `git add -A`를 쓰지 않는다.
   - 메시지: `R6e: p26_center_test 1.5 300 16 (raw logs, no code change)`
   - 현재 브랜치로 일반 push. 거부되면 `git pull --rebase` 후 한 번만 다시 시도한다.
     force push는 하지 않는다. 인증 문제로 실패하면 커밋은 로컬에 둔 채 보고한다.

## 하지 말 것

- 어떤 `.py` 파일도 수정하지 않는다. 버그처럼 보이는 것이 있어도 고치지 말고 보고에 적는다.
  코드가 바뀌면 이전 실험(R6)과 비교할 수 없게 된다. 실행 자체가 불가능해서 수정이
  불가피하면, 수정 전에 멈추고 필요한 diff를 제안만 한다.
- 다른 SNR, 다른 eta, 다른 ncw로 추가 실행을 하지 않는다.
- 로그에서 숫자를 뽑아 별도의 JSON이나 표를 만들지 않는다. 옮겨 적는 과정이 오류의 원천이다.
